# Firebase authentication and password recovery

Firebase Authentication handles email/password credentials, verification links and password-reset emails. Google sign-in and the website's secure HttpOnly session cookie remain supported. When `RESEND_API_KEY` and `EMAIL_FROM` are configured, verification links are generated by Firebase Admin and sent through Resend using your verified sender. This provides an alternate delivery path when Firebase's default sender is accepted but messages never reach the inbox. Firebase still validates the link and grants verified status; no database reimport is required.

Without a configured Resend sender, Firebase sends verification emails directly. A custom-send failure falls back to Firebase. Provider acceptance does not guarantee inbox delivery, so the UI reports a requested email and offers resend. Rejected sends allow an immediate retry. Signup saves the unverified account but never grants a session until verification succeeds.

To activate custom verification delivery in production, configure `RESEND_API_KEY` and `EMAIL_FROM` with a verified sending domain (see [email setup](email-setup.md)), deploy and restart with the updated environment, then test signup and resend using an inbox you control. Check Resend delivery/bounce events. Server logs distinguish `firebase_verification_accepted` by provider from delivery failures. Firebase REST rejections include only operation, HTTP status and a sanitized error code, never email addresses, action links or tokens.

## Existing accounts

- The current PBKDF2-SHA512 hashes cannot be imported directly. On the next successful legacy password sign-in, a missing Firebase identity is created with that password and original account ID. Profiles, paid memberships, progress and saved content stay intact.
- Firebase becomes authoritative once it has a password provider. An explicitly linked, verified Google identity without a Firebase password provider can still use its preserved application password. Once a Firebase password is set, the old application password is no longer accepted. A successful Firebase password sign-in removes the legacy hash from current app state; historical immutable chunks can still contain prior versions.
- Existing Firebase identities are reused only when UID bindings agree. Their passwords and Google providers are never overwritten. Users with Google-only identities can continue with Google or use Forgot password to add a Firebase password.
- Recovery before the first migrated login provisions a missing Firebase identity without a password. The user must complete the emailed reset before password sign-in can work. Requests have email/IP limits and generic responses. Delivery failures log no email, token or password.
- New email/password users and unverified legacy users must open the verification email before getting a website session. Google-proven emails stay verified. Firebase-bound website sessions are checked against identity deletion, disablement, email changes and Firebase token revocation, with a ten-second identity cache.


The Firebase project password policy was configured to require 8–128 characters, a number and a special character, matching signup. Forced upgrades on sign-in remain off. The hosted reset page follows this policy. Firebase quotas and abuse protection apply. No plan was upgraded and no live user email was sent during implementation. Verify inbox/spam delivery with your own account after deployment.

EMAIL_VERIFICATION_REQUIRED and EMAIL_OTP_SECRET are ignored for Firebase authentication. The Resend sender, when configured, handles both verification links and optional payment thank-you messages. Password recovery continues to use Firebase's native mailer. Firebase's default authentication mailer cannot send arbitrary purchase receipts.
