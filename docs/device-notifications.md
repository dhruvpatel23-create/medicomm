# Device notifications

Run `npm run setup:push` once to create a stable VAPID key pair in the ignored `.env.local`. The script preserves existing keys. For production, securely copy `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT` into the backend host environment, rebuild the frontend, and restart the server. Never put the private key in a `VITE_` variable or commit it. Keep keys stable across deploys; changing them requires devices to enable notifications again.

Serve the app over HTTPS. The first authenticated visit shows an opt-in card; tapping Enable opens the browser permission dialog. Settings lets users enable or disable the current device and separately control messages, challenges, and daily reminders across all their devices. Denied browser permission must be changed in site settings. iPhone/iPad users must add the app to their Home Screen and open it there. The existing web manifest supports this flow.

Subscriptions and the push outbox use the existing private state storage (Firebase, Supabase, or local storage). `/api/notifications` requires a session and the existing origin checks; only the public VAPID key is returned. Message content stays private: the notification says who sent a message without displaying its text. Logout unsubscribes this browser and removes its endpoint from the backend. An endpoint can belong to only one account at a time.

Message creation and real challenge creation save notification jobs in the same transaction. A challenge includes the sender's name, question count and subjects; clicking opens Compete, where incoming invitations can be accepted. Message notifications open the relevant inbox conversation; reminders open Practice. Repeated messages in one conversation and repeated challenges from one sender are limited to one alert per recipient per minute and use a replacement notification tag. Expired/cancelled challenges are skipped. No notifications are generated by polling the inbox.

An internal worker runs every minute and after message/challenge creation. Daily reminders start at 18:00 Asia/Kolkata (`PUSH_REMINDER_HOUR_IST`, 0–23), and go to subscribed accounts with the daily preference enabled. The target comes from the saved daily question goal in Settings. For older accounts with only a weekly study target, it uses that target divided by seven, rounded up; otherwise it defaults to 40, matching Study preferences. The body reports remaining questions using the same practice and duel activity counts as the dashboard. Completed goals are skipped. Both target and progress are refreshed just before sending. Each account's date marker is persisted before delivery, so repeated ticks, restarts, and goal changes cannot create another reminder that day. Each enabled device receives its own copy. Reminder delivery expires after one hour or at midnight India time, whichever comes first.

Provider registration accepts browser-issued public HTTPS endpoints, including long tokens, without a vendor hostname list. Delivery uses a custom HTTPS agent that resolves and pins public DNS addresses, rejecting loopback, private, link-local, reserved, and mixed public/private results. Literal IP endpoints receive the same checks. The transport does not follow redirects. This supports provider hostname changes without allowing subscriptions to target internal services.

Use an always-running backend. A sleeping host cannot send on schedule; a server starting after the configured hour can send that day's reminder, but does not backfill earlier days. Delivery depends on browser/OS push support and device settings. The worker claims each job durably before sending, favoring no duplicate alerts: a crash during delivery or a temporary provider/network failure can lose that alert instead of retrying an uncertain send. HTTP 404/410 subscriptions are removed. Other failures log only notification kind and status, never endpoint secrets or message content.

Validation: `node --test server/push.test.mjs server/friend-duels.test.mjs` and `npx vite build`. To smoke-test on HTTPS, sign in as two accounts on separate browser profiles/devices, enable notifications, background the recipient, then send a private message and a real challenge. Confirm links, repeat-event grouping, preferences, and logout removal. Inspect Settings to confirm setup is enabled. Live OS delivery needs a real push provider and cannot be verified with the isolated unit transport.
